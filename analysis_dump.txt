

# 0_Team_Pipeline_Overview.docx


Team Pipeline & Plan
Digital Platform for Farmer Procurement Registration, Slot Booking & Status Tracking — SIH Problem ID 26032
This document is for you, the team lead. It explains, in plain language, how the whole project will be built from day one to demo day, how the work is split across 6 people, and how the 6 pieces connect into one working app. Each teammate also gets their own separate, very simple, step-by-step document — hand those out after you've read this one.
1. The Big Picture — What We're Building
A mobile-first web app (works like an app but opens from a link, so no app-store delay) where a farmer can register, book a slot to sell grain, get notified, walk through the centre, get their grain quality-checked, and get paid — while tracking every step on their phone. There is also an admin screen for the procurement centre staff.
We are building 6 pieces ("modules"). Each piece is small enough for one person to own start to finish, but all 6 pieces talk to one shared database so the app feels like one product, not six.
2. Decisions Already Made (so nobody has to guess)
The working draft left some choices open for the team. Here are the defaults chosen so everyone can start building today. Your team can change any of these together, but don't build against a different stack on your own — it will break integration.
Decision
Choice
MVP scope
Build the 5 officially required pieces first (registration, slot booking, notifications, queue/capacity, payment status). Assaying (quality check) is a bonus 6th module — build it if time allows, but it is not what gets you disqualified if late.
Frontend
React (a JavaScript framework) styled with Tailwind CSS, built as a PWA (Progressive Web App) — one shared frontend project, one folder per module.
Backend
Node.js with Express (a JavaScript backend framework) — one shared backend project, one folder of routes per module.
Database
MongoDB (a flexible, easy-to-learn database) using Mongoose to define the data shapes.
Data source
Mocked data for land records, mandi capacity, and bank verification — NOT real government APIs. This is a hackathon; fake but realistic data is expected.
Real-time behaviour
Not true real-time. The app re-checks for updates every 30 seconds to a couple of minutes (called "polling"). This is simpler to build and works better on poor rural networks than always-on connections.
Code hosting
One shared GitHub repository, one branch per person, merged into 'main' regularly.
API testing tool
Postman (a free tool to test backend routes without needing the frontend finished).

5. Order of Work — Who Waits for Whom
Nobody can build 100% blind to the others — but the dependency order below tells you who needs a small 'starter version' from someone else before they can properly test.
	•	Day 1 (everyone, together): Team lead creates the GitHub repo, the empty React app, the empty Express app, and the MongoDB database. Everyone installs their tools (see each person's document, Section 2) and clones the repo. Agree on the exact data shapes in Section 4 above — do not change field names later without telling everyone.
	•	Days 2–4 (everyone, in parallel): Each person builds their own module against FAKE/dummy data first — nobody needs to wait. Module 1 (Registration) and Module 4 (Capacity Sync) should aim to finish a basic working version first, since Modules 2, 3, 5, 6 all depend on Farmer and Slot data existing.
	•	Day 5: First integration checkpoint. Module 2 (Slot Booking) connects to real data from Module 1 and Module 4 instead of fake data. This is the moment 'one farmer books one real slot' becomes possible end-to-end.
	•	Days 6–7: Modules 3, 5, 6 connect to real Bookings from Module 2 instead of fake data. Now notifications, quality checks, and payment status all react to real bookings.
	•	Day 8: Full integration test — one person walks through the ENTIRE farmer journey (register → book → get notified → get assayed → get paid) and everyone fixes whatever breaks.
	•	Day 9–10: Polish (loading states, error messages, mobile screen sizes), rehearse the demo, prepare slides/pitch.
💡 Adjust the day numbers to however many days/weeks you actually have — the ORDER (setup → build in parallel against fake data → connect Module 2 first → connect the rest → integrate → polish) stays the same whether it's a 10-day sprint or a 4-week build.
6. Team Process (keep it light)
	•	Daily 10-minute stand-up: each person says what they built yesterday, what they're building today, what's blocking them.
	•	Everyone pushes their code to their own branch at least once a day, and opens a Pull Request into 'main' — even if it's not finished. Small, frequent merges beat one giant merge at the end.
	•	Nobody edits another person's module folder without a quick message first.
	•	If two people need to change a shared data shape (Section 4), that's a team decision, not a solo one — it affects everyone.
7. What You Hand Each Teammate
Give each person ONLY their own module document (not this whole pipeline doc, unless you want them to see the big picture too — recommended for at least a quick skim). Each module document is self-contained: it explains, in very simple steps, what to install, what the module does, exactly what data fields to build, the order to build things in, how to test it alone, and how it connects to everyone else.

# 1_Module_Registration_Verification.docx


Module 1: Registration & Verification
Assigned to: Teammate A  |  Project: Farmer Procurement Platform (SIH 26032)
Welcome! This is your module. Nobody else on the team needs to touch this — it is fully yours from start to finish. This document explains everything in the simplest possible steps. Read it top to bottom once before you start typing any code.
1. Your Job, In One Sentence
💡 You build the sign-up flow — a farmer enters their details, and your code checks (or fakes checking) their land record and identity before letting them into the system.
Think of yourself as the 'front door' of the whole app. Every other module needs a farmer to already exist before it can do anything — so this module should be one of the first two finished (along with Module 4).
	•	A farmer opens the app and fills a simple form: name, phone number, village, land details.
	•	Your backend checks the land record against a MOCK dataset you create yourself (a small JSON file pretending to be the government database) — real government API integration is a 'nice to have', not required for MVP.
	•	If a farmer is a tenant/sharecropper (doesn't own the land), you give them a separate path where a local official/panchayat can 'co-sign' — for the hackathon, this can just be a checkbox + a second phone number, not a real verification system.
	•	If something doesn't match, don't block the farmer — flag their profile as 'needs manual review' so an admin can approve later. Never permanently reject someone at signup.
2. Tools to Install First (one-time only)
Do these once, in order, before writing any code. If you already have one installed, skip it.
	•	Install 'Node.js' (this lets your computer run JavaScript code outside a browser). Go to nodejs.org, download the LTS version, click through the installer.
	•	Install 'VS Code' (this is the text editor / app you will write code in). Go to code.visualstudio.com and install it.
	•	Install 'Git' (this lets you save and share your code with the team). Go to git-scm.com, install it, keep clicking 'Next' with defaults.
	•	Make a free GitHub account at github.com if you don't have one. Give your username to the team lead.
	•	Ask the team lead for the project's GitHub repo link. Open VS Code, open a Terminal inside it (Terminal menu → New Terminal), and type: git clone <the link they gave you>. This copies the whole project onto your computer.
	•	Install 'Postman' (a free tool that lets you test your backend code by sending it fake requests, without needing the app's screens built yet). Go to postman.com/downloads.
	•	Install 'MongoDB Compass' (a free tool to LOOK INSIDE the database visually, like a spreadsheet viewer, so you can see if your data actually saved). Go to mongodb.com/products/compass.
	•	Ask the team lead for the database connection link (it looks like mongodb+srv://...) and the shared .env file — this is a secret settings file that lets your code connect to the shared database. Never upload this file to GitHub.
3. Words You'll See a Lot (quick glossary)
	•	Frontend: the part of the app you SEE and click — buttons, forms, screens.
	•	Backend: the part of the app you DON'T see — it saves data, checks rules, and talks to the database.
	•	Database: where all the information is permanently stored, like a giant filing cabinet.
	•	API / Endpoint: a specific 'address' your backend listens on. Example: POST /api/farmers means 'send me a new farmer here'.
	•	JSON: a simple way of writing data as text, like { "name": "Ravi", "age": 30 }. Almost everything you send/receive will look like this.
	•	GET / POST / PUT: the 4 basic actions. GET = read data. POST = create new data. PUT = update existing data. DELETE = remove data.
	•	Schema / Model: the 'shape' of your data — which fields exist and what type they are (text, number, date, etc).
	•	Branch: your own private copy of the code to work in, so you don't break anyone else's work. You 'merge' it back in when ready.
	•	Mock / Dummy data: fake, made-up data you use to test your module before the real thing exists.

5. Step-by-Step: What to Build, In Order
Follow these steps in order. Don't skip ahead — each step is small on purpose so you always have something working.
	•	Create a folder backend/modules/registration. Inside it, define the Farmer schema (Section 4) using Mongoose.
	•	Build a small JSON file of 10–15 FAKE land records (name + fake land ID + 'valid'/'invalid') to stand in for the real government database. This is your mock dataset.
	•	Build the endpoint POST /api/farmers/register — it should: (a) receive the form data, (b) check the land ID against your mock file, (c) set land_record_status accordingly, (d) save the new Farmer, (e) return the saved farmer_id.
	•	Build the endpoint GET /api/farmers/:id — returns one farmer's full profile, so other modules (and your own frontend) can look someone up.
	•	Test both endpoints in Postman with at least 3 cases: a matching land record, a mismatched one, and a tenant/sharecropper.
	•	Build a very simple registration FORM screen in the frontend (just plain fields, doesn't need to look pretty yet) that calls POST /api/farmers/register.
	•	Build a simple 'manual review' list screen for admins — anyone with land_record_status = 'pending_review' shows up here so staff can approve them.
	•	Once this works end-to-end with fake data, tell the team — Modules 2, 3 and 6 are waiting on real Farmer records to exist.

7. How Your Module Connects to Everyone Else
	•	Module 2 (Slot Booking) needs a valid farmer_id before a farmer can book a slot — they will call your GET /api/farmers/:id.
	•	Module 3 (Notifications) reads the phone field from your Farmer record to know where to send messages.
	•	Module 6 (Payment Tracker) reads the farmer_id to link payments to the right person.
	•	You do NOT need anything from anyone else to start building — you're the starting point.
8. Common Mistakes to Avoid
	•	Don't rename a shared field (Section 4) without telling the whole team — everyone else's code will break silently.
	•	Don't hardcode fake data into your final version — always read/write from the real shared database once it's ready.
	•	Don't skip error handling — if a field is missing, your backend should say so clearly, not crash silently.
	•	Don't work for 3 days without pushing to GitHub — push small changes daily so nobody loses work.
9. How to Know You Are 'Done' (Testing Checklist)
	•	Open Postman. Send a request to each of your endpoints (Section 6) with made-up data. Check you get back a sensible response, not an error.
	•	Open MongoDB Compass. Confirm the data you sent through Postman actually appears in the database, in the right collection, with the right fields.
	•	Try to break your own module on purpose: send an empty field, send the wrong data type (like text where a number should go), send a duplicate. Your backend should reject it politely with a clear error message, not crash.
	•	Build a very simple screen (even an ugly one) in the frontend that lets you do the main action of your module without using Postman. This is what lets someone else on the team 'see' your module works.
	•	Write down (in a shared doc or on your GitHub Pull Request) exactly which endpoints you built and what fields they expect — this is what the rest of the team reads to connect to you.
10. Your Checklist Before Demo Day
	•	[ ] Every endpoint for Registration & Verification works when tested alone in Postman
	•	[ ] Your module's data appears correctly in MongoDB Compass
	•	[ ] Your simple screen works with REAL data from your teammates (not fake data anymore)
	•	[ ] You tried the full farmer journey once, start to finish, and your part didn't break it
	•	[ ] Loading and error states look okay, not blank/broken, on a phone-sized screen
	•	[ ] Your code is pushed to GitHub and merged into 'main'

9. How to Know You Are 'Done' (Testing Checklist)
	•	Open Postman. Send a request to each of your endpoints (Section 6) with made-up data. Check you get back a sensible response, not an error.
	•	Open MongoDB Compass. Confirm the data you sent through Postman actually appears in the database, in the right collection, with the right fields.
	•	Try to break your own module on purpose: send an empty field, send the wrong data type (like text where a number should go), send a duplicate. Your backend should reject it politely with a clear error message, not crash.
	•	Build a very simple screen (even an ugly one) in the frontend that lets you do the main action of your module without using Postman. This is what lets someone else on the team 'see' your module works.
	•	Write down (in a shared doc or on your GitHub Pull Request) exactly which endpoints you built and what fields they expect — this is what the rest of the team reads to connect to you.

	•	[ ] Your module's data appears correctly in MongoDB Compass

Project Integration & Readiness Report
Digital Platform for Farmer Procurement Registration, Slot Booking & Status Tracking — SIH Problem ID 26032 | For: Team Lead
This report is for you only. It explains, in the same very-basic step-by-step style as the module documents, exactly how the 6 separate modules become ONE working app, in what order to wire them together, how to test the whole thing, how to track everyone's progress, and how to know the project is actually ready for demo day. Follow the phases in order — don't jump ahead.
1. What 'Linking the Modules Together' Actually Means
Right now, each teammate is building their module as if it's the only thing that exists, using fake data. 'Linking together' means three concrete, physical things happening — not a vague idea:
	•	One shared backend program (not six separate ones) where every module's code lives in its own folder, and one small file (server.js) turns all 6 folders on at once.
	•	One shared database (not six) where every module reads and writes to the same collections, using the same field names, so a farmer created by Module 1 is the exact same farmer Module 6 pays.
	•	One shared frontend program (not six separate mini-apps) where every module's screens are reachable from one menu/navigation bar, so a judge clicks through ONE app, not six different browser tabs.
💡 If you remember nothing else from this report: integration is NOT a single last-day event. It happens in small steps throughout the build, starting from Day 1. Trying to combine 6 untested pieces on the final day is the single biggest risk to this project.
2. The Physical Wiring — Exactly How Code Connects
This section is slightly technical — read it once so you understand what you're asking teammates to do in Phase 2 onward. You don't have to write this code yourself, but you should understand it well enough to review it.
2.1 Backend wiring (one file mounts everyone's work)
Your shared backend has one main file, usually called server.js or app.js. Every module's routes get 'mounted' onto it with one line each, like this in plain English: "Anything sent to an address starting with /api/farmers, hand it to Module 1's code. Anything starting with /api/bookings, hand it to Module 2's code." This is why every module document tells each teammate their exact endpoint addresses — those addresses are what gets wired here.

2.2 Database wiring (one database, shared shapes)
All 6 modules point at the exact same database connection string (the .env file you shared in setup). There is nothing extra to 'wire' here beyond making sure everyone used the same field names from each module document's Section 4 — this is why changing a shared field name without telling the team is the most common way integration breaks.
2.3 Frontend wiring (one app, one menu)
Your shared frontend has one navigation bar or bottom-menu. Each module's screens become one menu item: Register, Book a Slot, My Notifications, (Admin) Centre Dashboard, (Admin) Quality Check, Payment Status. Each teammate builds their screens as a self-contained 'page' component; you (or whoever owns the frontend shell) add one line per module to the shared navigation to make it reachable.
2.4 Cross-module calls (the 'nervous system')
Besides sharing a database, a few modules need to directly tell another module something happened. These are small, specific calls — not a rebuild:
	•	Module 2 (Booking) calls Module 4's slot-increment endpoint whenever a booking is made, so booked_count stays accurate.
	•	Module 2 (Booking) calls Module 3's notification-trigger endpoint whenever a booking is made, missed, or rescheduled.
	•	Module 6 (Payment) calls Module 3's notification-trigger endpoint whenever a payment status changes.
	•	Module 6 (Payment) optionally calls Module 5's GET assay-result endpoint to help calculate a payment amount.

Follow these 7 phases in order. Each phase lists exactly what YOU do as team lead, and what you're waiting on from the team before moving to the next phase.

	•	Create one GitHub repository for the whole project (not six). Name it clearly, e.g. sih-farmer-procurement.
